Implement P1 Optimization: Server-Side Joins for Deposit Customer Names.

## Findings & Decisions
- Added strict global protection rules against running destructive/reset database commands against production to `.agents/conventions.md`.
- Implemented **P1: Server-Side Joins for Deposit Customer Names**:
  - Created a new SQL migration file `supabase/migrations/20260902000000_server_side_joins.sql` modifying `one_time_deposit_details_view` and `recurring_deposit_details_view` to join with the `customers` table and return `customer_name`. It safely drops the existing views with `CASCADE` first to prevent PostgreSQL schema change failures when executed against a live production database.
  - Added the optional `customerName` getter to the `BaseDeposit` interface.
  - Added `@JsonKey(includeFromJson: true, includeToJson: false) String? customerName` to Freezed `OneTimeDeposit` and `RecurringDeposit` models. This allows automatic deserialization of `customer_name` when reading from Supabase views, but avoids serializing it on writes/saves.
  - Re-generated Freezed and JSON serialization classes using `build_runner`.
  - Optimized the Riverpod `filteredOneTimeDeposits` and `filteredRecurringDeposits` providers:
    - Designed an extremely efficient fallback pattern: if any deposits are retrieved with `customerName == null` (e.g. when using Firebase/Firestore without pre-joined views), it falls back to looking up the name in a client-side customer map built from `customersControllerProvider`.
    - If all deposits contain a pre-joined `customerName` (which is always true under Supabase), it **bypasses watching/loading `customersControllerProvider` entirely**. This eliminates client-side cross-fetching and completely prevents loading the entire list of customers, maximizing network efficiency, minimizing memory footprint, and avoiding unneeded database reads.
