# Session Log: 2026-08-30 (Session 3)

## Summary
Resolved migration performance bottlenecks for agents with large datasets (600+ customers) by transitioning from sequential single-row inserts (causing extensive N+1 HTTP overhead) to an optimized, transaction-safe bulk insert strategy.

1. **Bottleneck Analysis**:
   - The previous implementation executed asynchronous HTTP insert requests sequentially within nested loops (e.g., executing `insert` for every customer, savings account, deposit, and nominee).
   - For an agent with 600 customers, this resulted in 1,000 to 2,500 individual network roundtrips, resulting in extremely slow migrations and potential connection dropouts.
   - Frequent sequential calls to `_log` flooded the console/UI, adding substantial rendering overhead and choking the application's main thread.

2. **Bulk Insertion Strategy & Client-Side UUID Mapping**:
   - Since all entity IDs (UUIDs) are deterministically or randomly generated on the client side (`_toUuid()` or `const Uuid().v4()`), we can map out all foreign keys and relationships entirely in-memory before writing to the database.
   - Redesigned `_runDataMigration` to aggregate entries across 6 distinct tables into separate list-based batches:
     - `customersBatch`
     - `accountIdentitiesBatch`
     - `savingsAccountsBatch`
     - `otdsBatch`
     - `rdsBatch`
     - `nomineesBatch`

3. **Incremental Progress Chunking**:
   - Implemented an elegant `_insertInChunks()` helper that performs bulk table writes in chunk sizes of 200.
   - This ensures excellent visual progress feedback in the migrator logs (e.g. `Inserted chunk 1/3`) while fully guarding against HTTP payload size and PostgreSQL connection limits.
   - Maintained complete relational foreign key integrity by executing the chunked insertions in exact dependency order:
     1. `customers`
     2. `account_identities` (depends on `customers`)
     3. `savings_accounts`, `one_time_deposits`, `recurring_deposits` (depend on `account_identities`)
     4. `nominees` (depends on `account_identities` via `account_id`)

4. **Performance Outcome**:
   - Reduced the number of database network roundtrips for 600 customers and associated deposits from ~2,500 down to roughly **12-15 roundtrips** (a up to **99.5% reduction**).
   - Expected bulk migration speeds are accelerated by **100x to 1000x**, taking seconds instead of several minutes.
   - Restored smooth UI frame rendering during bulk migrations by suppressing individual row-level logs and outputting chunk-level summaries.

5. **Polymorphic Parent ID Namespace Resolution**:
   - Identified and resolved a second unique constraint violation on `account_identities.id` occurring when migrating multiple agents.
   - *Root Cause:* In Firestore, `oneTimeDeposits` and `recurringDeposits` exist in separate isolated subcollections, meaning an agent could have an OTD with document ID `'1'` and an RD with document ID `'1'`. When migrated to Supabase, both OTDs and RDs are unified under the same polymorphic parent table `account_identities`. This caused a primary key collision when attempting to write `_toUuid('1', prefix: fUid)`.
   - *Solution:* Upgraded the deterministic UUID generation namespace to isolate by entity type:
     - Customers prefix: `$fUid/customer`
     - One-Time Deposits prefix: `$fUid/otd`
     - Recurring Deposits prefix: `$fUid/rd`
   - Fully prevents cross-type primary key collisions on the shared parent tables while preserving accurate database mapping and referential foreign keys.

6. **Idempotency & Upsert Hardening**:
   - Refactored `_insertInChunks` to utilize `.upsert()` (PostgreSQL `ON CONFLICT (id) DO UPDATE`) instead of `.insert()`.
   - This ensures the entire data migrator is 100% idempotent. If a migration is interrupted or run twice, existing records are cleanly merged/updated rather than crashing the tool with unique constraint violations.

7. **Transparent Skipped-Record Console Logs**:
   - Added specific console-level `_log` output strings whenever a record (Customer, SB Account, OTD, or RD) is skipped because it already exists in the target Supabase database.
   - Surfaces real-time, high-fidelity visual indicators (e.g. `-> Skipped existing Customer: Darshan (UUID: ...)`) inside the visual migrator console, providing excellent debugging feedback.
