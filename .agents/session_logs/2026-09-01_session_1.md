# Session Log: 2026-09-01 (Session 1)

## Summary
Investigated and resolved a root-cause duplicate key constraint violation on `account_identities.id` and `savings_accounts.id` during programmatic data migrations when multiple customers share the same savings account number (e.g. joint accounts, family members, or duplicates in legacy records).

1. **Unique Constraint Analysis**:
   - In PostgreSQL, the `savings_accounts` table is related 1-to-1 with `account_identities` via its `id` column, which is a foreign key pointing to `account_identities(id)`.
   - `account_identities` represents an identity/reference of an account belonging to a specific customer (`customer_id`).
   - Thus, every customer with a savings account must have their own unique `account_identities` and `savings_accounts` records.
   - However, in our legacy migration script (`lib/run_supabase_migration.dart`), the UUID for the savings account (`saAccountId`) was generated deterministically using the **savings account number**:
     ```dart
     final saAccountId = _toUuid(saAccountNumber, prefix: '$fUid/savings_account');
     ```
   - This caused multiple customers sharing the same savings account number (e.g. a joint account) to resolve to the same `saAccountId`.
   - When migrating multiple customers with the same account number, this resulted in:
     - Attempting to map the same `saAccountId` to different `customer_id`s, causing a **primary key unique constraint violation** on `account_identities.id` (duplicate key error).
     - Or, if pre-filtered, silently skipping the savings account for the subsequent customers, leading to missing data.

2. **Resolution & Deterministic Mapping**:
   - Upgraded the `saAccountId` generation to be seeded by the unique **customer's ID** instead of their savings account number:
     ```dart
     final saAccountId = _toUuid(customer.id, prefix: '$fUid/savings_account');
     ```
   - Because every customer document in Firestore has a guaranteed unique `id`, this produces a unique `saAccountId` for every customer.
   - Allows multiple customer records to securely share the same physical savings account number without colliding on primary key/unique constraints in PostgreSQL.
   - Seamlessly aligns with our pre-joined SQL views and the transactional RPC writes (which identify savings accounts on a per-customer basis using `upsert_account_identity`).
   - Verified that the system compiles perfectly with no analyzer diagnostics (`flutter analyze`) and all unit tests continue to pass 100% green (`flutter test`).
