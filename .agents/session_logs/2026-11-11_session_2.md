## Findings (fix before merge)
1. `RDLedgerController.depositBatchToPo` returns Failure when a post-commit facts read fails; a retry deposits the same months again. About 10 sequential reads per account; `fetchRawFactsForRds` is not used here.
2. The visit sheet's "include unready" switch re-seeds the planner from every Hub row, discarding the batch selection.
3. `.github/workflows/backup.yml` expands `$DATABASE_URL` on the runner where it is unset; the step exits under `set -u`.
4. Enum CHECKs were dropped while Dart decodes enums strictly and `SupabaseErrorMapper` discards the original error; one bad row blanks a list.
5. The financial-terms lock in `RecurringDepositsController.saveRecurringDeposit` fails open; the SQL check was removed in Stage 5.
6. The consolidated migration has only run against the 3-customer seed and contains a destructive SB dedup `DELETE` plus constraints that abort on bad existing rows. `release.yml` has no migration step.

## Other Notable Findings
- `ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ... FROM PUBLIC` does not remove PUBLIC's built-in EXECUTE: a function created after the migration was executable by `anon` (probe result).
- `SupabasePaginatedQuery` channels never refetch on resubscribe, drop a queued refetch when the in-flight fetch throws, and never retry a failed first load.
- Coverage gate: the data floor is met by fakes (Supabase repositories are uncovered in the gated run) and the domain floor relies on `lib/core/widgets/domain/` matching the `/domain/` substring.
- Customer delete and undo-visit are multi-request, non-atomic sequences.
